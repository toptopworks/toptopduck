# 结果渲染架构：行服务端分页 + 列原生全量 + 数值类型对齐，不引入虚拟化/跳页/column cap

## Decision

ResultView（ADR-0045 workspace「结果」tab 的核心舞台）的渲染架构定下三块，**均不引入虚拟化**：

**（1）行方向——服务端分页，不虚拟滚动、不跳页**
- 维持 `readRows` 服务端分页（`DEFAULT_PAGE_SIZE=100`，ADR-0024），前端每页恒渲染 ≤ 100 `<tr>`。
- `row_cap = DEFAULT_MAX_RESULT_ROWS`（100 万，`guardrail.rs`）超限 **abort 成 Resource error、不截断**（ADR-0030）——前端永远拿不到半结果。
- 超大结果（行数 > 披露阈值，精确值留实现期）顶部出**披露横幅**："此结果较大（N 行），分页显示中；想看特定部分可继续提问"——把"全量/精准导航"导向自然语言重定向（ADR-0010），不导向 v1 尚不存在的 export（ADR-0024 纸面）。
- 否决跳页（"跳到第 N 页"）与行虚拟滚动。

**（2）列方向——原生全量 + 横向滚动 + 列数披露，不虚拟化、不加 column cap**
- `RowPage.columns` 全量返回（`types.ts`），`ResultView` 全量 map `<th>/<td>`；列多靠横向滚动（ADR-0054 workspace 表格横滚而非挤 rail）。
- 列数超阈值（如 100）顶部出披露"此结果含 N 列"——守 ADR-0030/0033 不静默。
- **不加 column cap**（类比 row_cap）——列是数据固有形状，截断列破坏数据语义；abort 会让"分析这张宽表"直接失败，违 ADR-0001。

**（3）单元格——按 `canonical_type` 数值列右对齐 + NULL 灰显，内容不格式化**
- 用 `ColumnSchema.canonical_type` 识别 DuckDB 数值类型集，数值列 `<td>` 右对齐，其余左对齐。
- 内容字节不变（守 ADR-0052 第②层"数据表单元格保持原样"——千分位/小数位/日期格式化仍被否决；对齐是布局属性，非内容格式化）。
- NULL 单元格（服务端 `NULL → ""`）灰显空位，不填 "NULL" 字样（免误导，呼应 ADR-0030/0017 诚实性）。
- 列头不显示类型（`BIGINT` 等对非技术用户是噪音，违 ADR-0001）。

## Context

ADR-0045（两栏 shell）/ 0051（状态分层）/ 0024（windowed display + row pages）定了 ResultView 的容器、数据契约、分页管道，但**渲染策略本身（行/列/单元格三方向怎么落到 DOM）从未被任何 ADR 决策**。`ResultView.tsx` 现状是脚手架默认（原生 table + 上一页/下一页 + 全左对齐），非有意识架构。本 ADR 收口渲染架构，并显式记录"为什么不虚拟化"——这是最易被未来工程师"好心补上"的否决项。

关键代码事实驱动了决策反转：行方向被 `row_cap` + abort + 服务端分页三重保护（前端每页恒 ≤ 100 行），**渲染瓶颈不在行在列**；而列方向零保护、零 cap、全量返回。

## Why

1. **ResultView 是探查舞台，不是全量浏览器**——用户看头/样/分布、确认 LLM 理解对了；"找第 N 行"靠自然语言重定向（ADR-0010），不靠 UI 导航。这是行/列都不虚拟化的领域根据。
2. **行三重保护使虚拟滚动无必要**——`row_cap` abort + 分页 100/页，前端 DOM 恒轻；虚拟滚动是为"前端持有大行集"准备的，本项目服务端持有、前端只持一页。
3. **跳页是非技术用户(ADR-0001)次优心智**——"我要的在第几页"是 DBA 算法（ADR-0045 已否决 DB 工具壳）；非技术用户不会算页码。
4. **column cap 语义错**——行 cap 保护物化代价（abort 合理），列是数据形状（截断 = 破坏语义）。
5. **数值右对齐是近乎免费的可读性收益**——内容不变（守 0052 第②层），只切 CSS 类；列头不带类型守 ADR-0001。
6. **披露而非静默**呼应 ADR-0030/0033——超大结果/超多列明示，不假装轻松。

## Considered options

- **列虚拟化（react-window grid 变体）**：视口外列不渲染。与未来列宽调整/排序/冻结列耦合深，v1 这些功能未决策（YAGNI）；非技术用户宽表多在数十到一两百列，100×200 = 2 万 `<td>` webview 可承受。**否决**，留 v2（300+ 列痛点出现时重评）。
- **column cap（类比 row_cap）**：列是数据固有形状，截断破坏语义；abort 让"分析宽表"直接失败违 0001。**否决**。
- **行虚拟滚动**：服务端分页已使前端 DOM 恒轻，虚拟滚动为解决不存在的问题。**否决**。
- **跳页（跳到第 N 页/行）**：DBA 心智、违 0001 + 0045 DB 工具壳否决。**否决**。
- **类型感知格式化（千分位/日期）**：违 ADR-0052 第②层"数据表单元格保持原样"。**否决**——仅取对齐（布局层），不取格式化（内容层）。
- **列头显示类型**：`BIGINT` 等对非技术用户是噪音、违 0001。**否决**。

## Consequences

- **前端实现**：`ResultView` 维持原生 `<table>` + 服务端分页；新增 (a) 列数披露 + 行数披露横幅（复用 `DisclosureBanner` 模式，ADR-0033）、(b) `canonical_type` → 数值类型集映射 → 数值列右对齐 CSS、(c) NULL 灰显。
- **数值类型集映射**：前端维护 DuckDB 数值类型集合（`TINYINT/SMALLINT/INTEGER/BIGINT/HUGEINT/UTINYINT.../FLOAT/DOUBLE/REAL/DECIMAL`）→ 右对齐；精确集合留实现期。
- **披露阈值留实现期**：行数/列数披露的精确阈值（如行 > 1 万、列 > 100）是视觉迭代、非架构。
- **延伸 ADR-0052 第②层**：明确"保持原样"指内容字节不变；**对齐（布局属性）不在其列**——数值列右对齐与第②层相容。
- **延伸 ADR-0045/0051**：ResultView 作为 workspace「结果」tab 的渲染落点定案；与 0051 per-tab hidden 保活 + Vega `ResizeObserver`（0051）兼容——原生 table 无 Vega 的 resize 钩子需求，二者同区域共存无碍。
- **跨切面线索（留后续 ADR，非本 ADR）**：超大结果体验的根解在 **LLM 默认产出"可浏览量级"**——system prompt 引导 LLM 对"显示全部"类请求默认 `LIMIT` + 披露"已显示前 N 行，如需更多请说明"。这是 ADR-0009 契约 / ADR-0017 诚实披露层的事，前端披露只是其 UI 落地。
- **顺带观察（偏后端，非本 ADR）**：`row_cap` 默认 100 万对"非技术用户桌面分析"偏高（更像安全阀而非 UX 锚点）；属引擎配置范畴，留 ADR-0005 L3 后续。
- **出口保留**：300+ 列宽表成主流痛点 → 列虚拟化重评；"非技术用户需频繁翻大结果"成真实场景 → 跳页/虚拟滚动重评。二者均 v2。
- **CONTEXT.md 不动**：渲染架构是实现决策，不引入新领域术语；"探查舞台 vs 全量浏览器"是 UI 定位（ADR rationale），非领域概念。
